1. Introducción teórica

1.1 ¿Qué es Git?

Git es un sistema de control de versiones distribuido. Permite registrar todos los cambios que se hacen en los archivos de un proyecto a lo largo del tiempo, de forma que se puede saber quién hizo cada cambio, cuándo y por qué, y volver a cualquier versión anterior si es necesario.

Es distribuido porque cada desarrollador tiene en su equipo una copia completa del repositorio con todo su historial. Los cambios se comparten con el resto del equipo a través de un repositorio remoto, en nuestro caso alojado en GitHub.

Conceptos básicos que hemos utilizado:

  • Repositorio: carpeta del proyecto cuyo historial gestiona Git.
  • Commit: instantánea de los cambios guardada en el historial, con un mensaje que la describe.
  • Rama (branch): línea de desarrollo independiente que permite trabajar sin afectar al resto del código.
  • Merge: integración de los cambios de una rama en otra.
  • Tag: etiqueta que marca un commit concreto, normalmente una versión publicada (por ejemplo v1.0).
  • Push / Pull: enviar cambios al repositorio remoto / traer cambios desde él.

1.2 ¿Qué es Git Flow?

Git Flow es una metodología de trabajo con ramas que define qué ramas existen en un proyecto, para qué sirve cada una y cómo se integran entre sí. Se organiza en dos ramas principales permanentes y tres tipos de ramas de apoyo temporales:

RamaTipoSale deSe integra enFunción
mainPrincipal——Contiene solo código estable, listo para producción. Cada versión publicada se marca con un tag.
developPrincipalmain—Rama de integración donde se van juntando las nuevas funcionalidades terminadas.
feature/*ApoyodevelopdevelopDesarrollo de una nueva funcionalidad de forma aislada.
release/*Apoyodevelopmain y developPreparación de una nueva versión: últimos ajustes antes de publicarla y etiquetarla.
hotfix/*Apoyomainmain y developCorrección o mejora urgente sobre la versión ya publicada, sin esperar a la siguiente release.

Para aplicar la metodología hemos usado la extensión git-flow, que automatiza la creación y el cierre de estas ramas con comandos como git flow feature start o git flow release finish.

1.3 ¿Por qué utilizamos Git Flow?

  • Trabajo en paralelo: cada programador desarrolla su sección en su propia rama feature sin interferir en el trabajo de los demás.
  • Código estable siempre disponible: main solo recibe código revisado a través de releases y hotfixes, así que el cliente siempre tiene una versión que funciona.
  • Versiones identificadas: cada versión publicada queda etiquetada (v1.0), por lo que es fácil saber qué contiene y volver a ella.
  • Correcciones rápidas: las ramas hotfix permiten mejorar la versión publicada sin arrastrar trabajo a medias de develop.
  • Trazabilidad: el historial muestra con claridad qué se hizo, en qué rama y quién lo hizo, lo que demuestra al cliente que trabajamos siguiendo una metodología.

El equipo está formado por 3 programadores. Para simularlos se ha configurado el nombre de cada uno con git config user.name antes de su trabajo, y además se indica su nombre en cada mensaje de commit.

3. Convención de mensajes de commit

Todos los commits siguen el formato Conventional Commits:

tipo(ámbito): descripción en imperativo [Usuario X]
TipoUso
featNueva funcionalidad.
styleCambios de estilos o aspecto visual.
fixCorrección o mejora de algo existente.
choreTareas de mantenimiento, como preparar una versión.
docsDocumentación.

La descripción es breve, está en imperativo ("añadir", "crear") y termina con el nombre del usuario entre corchetes para identificar quién realizó el cambio.

4. Proceso realizado

4.1 Usuario 1 – Creación del repositorio y estructura inicial

El Usuario 1 crea el repositorio curso-js-interacciones en GitHub, lo clona en su equipo, configura su nombre e inicializa Git Flow. Al ejecutar git flow init se crean las ramas iniciales: main como rama de producción y develop como rama de desarrollo. 

git clone https://github.com/Sergiete07-1/curso-js-interacciones.git
cd curso-js-interacciones
git config user.name "Usuario 1"
git flow init

A continuación implementa la estructura inicial de la web: cabecera con el nombre del curso e imagen de fondo, barra de navegación con acceso a Home, una breve descripción del curso en la parte central y el pie de página. El menú se genera desde js/menu.js para que cada sección nueva solo tenga que añadir su enlace.

El trabajo se guarda en dos commits y se suben ambas ramas a GitHub:

git add index.html js
git commit -m "feat(home): crear estructura con cabecera, menú y footer [Usuario 1]"
git add css img
git commit -m "style(home): añadir estilos e imagen de cabecera [Usuario 1]"
git push -u origin main develop

4.2 Usuario 2 – feature/contenidoHTML

El Usuario 2 crea la feature desde develop para implementar la sección "Modificar contenido HTML", con un ejemplo similar al de W3Schools: al pulsar un botón, JavaScript cambia el texto de un párrafo mediante la propiedad innerHTML. 

git config user.name "Usuario 2"
git flow feature start contenidoHTML
git add .
git commit -m "feat(contenido): añadir sección Modificar contenido HTML [Usuario 2]"
git push -u origin feature/contenidoHTML
git flow feature finish -k contenidoHTML
git push origin develop

4.3 Usuario 2 – feature/atributosHTML

Con el mismo procedimiento, el Usuario 2 crea una segunda feature para la sección "Modificar atributos HTML". El ejemplo enciende y apaga una bombilla cambiando el atributo src de una imagen. 

git flow feature start atributosHTML
git add .
git commit -m "feat(atributos): añadir sección Modificar atributos HTML [Usuario 2]"
git push -u origin feature/atributosHTML
git flow feature finish -k atributosHTML
git push origin develop

4.4 Usuario 3 – feature/estilosCSS

El Usuario 3 crea su feature para la sección "Modificar estilos CSS", con un ejemplo similar al de W3Schools en el que JavaScript cambia el tamaño de la letra de un párrafo a través de la propiedad style. El código está comentado explicando cada paso. 

git config user.name "Usuario 3"
git flow feature start estilosCSS
git add .
git commit -m "feat(estilos): añadir sección Modificar estilos CSS [Usuario 3]"
git push -u origin feature/estilosCSS
git flow feature finish -k estilosCSS
git push origin develop

4.5 Usuario 3 – release/v1.0

Con las tres features integradas en develop, el Usuario 3 crea la release v1.0. En ella marca la versión en el pie de la página Home. Al cerrarla, Git Flow la integra en main, crea el tag v1.0 y lleva ese tag de vuelta a develop. 

git flow release start v1.0
git add .
git commit -m "chore(release): preparar versión 1.0 [Usuario 3]"
git push -u origin release/v1.0
git flow release finish -k -m "Versión 1.0 [Usuario 3]" v1.0
git push origin main develop --tags

4.6 Usuario 1 – hotfix/mejorasV_1_0

El Usuario 1, encargado de las pruebas, decide mejorar la sección de contenido creada por el Usuario 2 añadiendo un botón "Restaurar" que devuelve el texto a su valor original. Como la mejora se aplica sobre la versión ya publicada, se usa un hotfix, que parte de main y al cerrarse se integra tanto en main como en develop. 

git config user.name "Usuario 1"
git flow hotfix start mejorasV_1_0
git add .
git commit -m "fix(contenido): añadir botón para restaurar el texto [Usuario 1]"
git push -u origin hotfix/mejorasV_1_0
git flow hotfix finish -k -n mejorasV_1_0
git push origin main develop

4.7 Resultado final del historial

Las tres features aparecen en línea sobre develop porque cada una tenía un único commit y Git Flow las integró mediante fast-forward. Las etiquetas feature/... junto a cada commit demuestran que cada una se desarrolló en su propia rama, que se ha conservado en el repositorio.
